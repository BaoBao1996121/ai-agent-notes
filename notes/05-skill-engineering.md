# 05 · 把重复做法写成可验证的 Skill

> 来源：原教程 Ch07 与三个本地工程方法；2026-11-09 整理。

一个值得保存的 Skill，应帮助完成某类反复出现的任务：知道什么时候用，输入是什么，怎么做，何时停止，怎样判断结果。它不因为篇幅长或用了很多“必须”就更可靠。

## 从一个真实失败开始

假设技术选型报告列了十个工具，却没有回答该选哪个。可提炼的做法是“先确认硬约束，再排除不满足的候选，给出条件化推荐”。这比再添加“请认真、全面、专业”更容易检查。

```text
触发：用户确实需要在多个技术方案中作决定。
输入：目标、已有条件、关键约束和候选。
过程：复用已有事实 → 核验变化信息 → 淘汰 → 比较 → 推荐。
输出：首选、原因、代价、备选触发条件、证据缺口。
停止：结论足够支持当前决定；不为填满模板继续调研。
```

可用版本见 [选型方法](https://github.com/BaoBao1996121/agent-engineering-playbook/blob/main/skills/tech-selector/SKILL.md)。

## 哪些内容值得写进指令

写下容易被误解的边界、影响结果的条件、必要的操作步骤，以及判断成功的办法。解释原因有助于理解规则，但权限和数据保护不能只靠“解释 Why”，仍需运行器、访问控制或审查落实。

触发条件要准确，不必把所有近义词和所有相邻任务都包进来。过宽触发会让一个小问题带上不需要的流程；过窄则漏掉真正适用的情况。

如果某一步是稳定、确定、反复执行的操作，可以考虑脚本化。先检查现有工具能否完成，不为封装再建一套平台。

## 怎么验证和淘汰

至少准备三类样例：应该触发、相似但不该触发、信息缺失或工具不可用。既检查产物质量，也观察有没有多余追问、越权读取、无效步骤和错误的完成声明。

一个 Skill 在三条样例上通过，不代表它在所有任务上可靠。保留失败案例，变更后复测相关情境；规则长期没有收益、与现有能力重复或造成过度流程时，应缩减或移除。

## 小模板

```markdown
# 方法名称

解决什么问题：
什么时候使用：
已知输入和不能猜的事项：
执行步骤：
结果与验证：
适用边界：
```

练习：把最近一次真实返工写成“触发条件→错误→有效修法→验证证据”。只有能跨相似任务复用的部分，才进入 Skill。
