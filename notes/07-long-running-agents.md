# 07 · 长任务的可靠性来自状态、验证和控制

> 来源：原教程 Ch09 与本地长任务脚手架；2026-11-09 修订。

长任务可能遇到上下文不足，也可能因为权限、并发、环境、验收不清或错误恢复不当而失败。不能把所有可靠性问题归因于一个窗口大小。

## 怎样让下一次会话接得上

持久记录至少要回答：目标是什么、做到哪了、证据在哪里、哪些限制仍然有效、下一步是什么。Git 记录文件变化，任务记录解释这些变化与目标的关系，二者互补。

[Anthropic 的长任务工程文章](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) 展示了初始化与后续增量执行分工，并使用进度文件和 Git 历史交接。这是一种可借鉴方式，不意味着每个任务都需要两个并行 Agent。

## 一份最小交接记录

```text
目标：让读者从首页找到全部已发布文章。
已完成：首页与章节链接已生成。
验证：本地相对链接检查通过；远端尚未核验。
未完成：上传后验证匿名读取。
注意：不要修改尚未审阅的原始笔记。
下一步：检查目标仓库默认分支上的首页和章节。
```

“代码完成”“本地验证”“已上传”“用户可以使用”可能处于不同状态。把它们压缩成“搞定了”，下一次就失去判断基础。

## 记录不是强制机制

把验收写进 JSON 有助于程序处理，但 JSON 本身不会阻止 Agent 修改目标。真正的限制来自文件权限、外部检查、受保护的评估器或人工审批。自动检查只有确实接入、覆盖该路径且不能被绕过时，才能约束交付。

同样，摘要只是有损的接续材料。发生冲突时，应核对当前事实与原始证据，而不是让旧摘要覆盖新状态。

## 增量推进的节奏

1. 读取当前状态，确认真实目标和授权仍然适用。
2. 选一个有明确验收的下一步，保全已有成果。
3. 执行后验证用户需要的结果。
4. 保存必要决定与证据，再继续下一步。

小改动通常不需要完整工作流。只有任务确实跨会话、容易失去状态时，才采用 [交接模板](https://github.com/BaoBao1996121/agent-engineering-playbook/blob/main/templates/handoff.md)。

## 练习

把一项正在进行的任务交给“完全没有聊天上下文”的未来自己。只留下半页记录和必要证据入口。过一天再读，检查是否能确定下一步、是否会重复已经失败的尝试、是否分得清验证和猜测。
