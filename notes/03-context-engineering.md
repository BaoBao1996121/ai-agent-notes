# 03 · 上下文工程：让模型找到判断所需的信息

> 来源：原教程 Ch05；公开版移除了未附原始产物的性能数字与内部项目例子。

上下文管理要同时处理三件事：信息是否完整、是否与当前问题相关、是否还能追溯到来源。目录索引帮助定位，原文帮助核实，二者承担不同职责。

## 把材料分成导航与证据

| 信息层 | 放什么 | 何时读取 |
|---|---|---|
| 任务约束 | 目标、授权、验收、当前边界 | 开始及约束变化时 |
| 全局导航 | 模块职责、文档目录、权威入口 | 需要定位时 |
| 局部接口 | 相关数据结构、调用关系、依赖签名 | 确定影响范围时 |
| 焦点证据 | 当前实现、测试、完整相关文档 | 作出具体判断前 |
| 接续状态 | 已完成、未完成、决定与证据位置 | 跨会话继续时 |

这不是固定 Token 配额。模型、任务、文本语言、工具结果和输出预算都会影响可用空间。用字符数除以四估算中文材料，只能算很粗的猜测；需要精确预算时，应使用对应分词器或平台返回的实际用量。

## 一次局部修改该怎么读

假设函数 A 调用了 B，B 又依赖大量通用工具。先读 A 的完整逻辑、B 的接口与相关实现，再决定是否需要展开后续依赖。不要机械规定“一层一定够”，也不要为了保险把全仓代码都塞进一次输入。

选择下一份材料时，可以问：**它会改变哪项判断？** 如果答案是“验证 B 是否会写数据库”，就读取 B 的写入路径；如果只是“它可能也有关”，先保留为候选。

有一个例外必须提前说明：如果任务要求完整审阅指定材料，不能用相关性筛选代替全文阅读。应分段读完并记录覆盖范围；空间不够时接续阅读，而不是把摘要当作原文。

## 上下文缩减时容易丢什么

- 摘要保留了结论，丢掉适用版本和例外。
- 只保留函数签名，丢掉隐藏的写入或错误处理。
- 只保留一次成功，丢掉先前失败和已排除假设。
- 交接记录写“修好了”，没有实际测试与部署状态。

因此，压缩后至少要留下来源位置、结论条件、尚未验证的部分。需要精确数字和原话时回到原始材料，不从压缩摘要反推。

## 一个可直接使用的上下文清单

```text
目标：这次要完成什么？
边界：哪些文件、系统和操作属于范围？
入口：当前权威材料在哪里？
已读：完整读取了哪些材料？
证据：支持当前判断的具体结果是什么？
缺口：哪些信息尚未读取或无法取得？
下一步：读取或验证什么能消除这个缺口？
```

练习：找一个你熟悉的小项目，只写一页导航，然后请另一位读者定位一个错误处理分支。记录他缺了哪些信息，再改导航。目标是帮助找到原文，而不是用导航替代原文。
